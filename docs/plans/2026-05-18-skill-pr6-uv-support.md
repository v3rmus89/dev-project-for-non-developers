# Skill PR #6 — uv support for Python

> Adds `--package-manager={uv,pip}` to the `dev-project-setup` skill's Python language. **uv is the new default for greenfield Python projects**; pip-venv stays supported for adoption-into-existing-projects + explicit opt-out. Auto-detection picks the right mode when applying onto an existing project. Mirrors PR #3's structural pattern (additive variant within an existing language, not a new language).

## Context

PR #1–#5 shipped: Python (PR #1), Node-TS (PR #2), Go (PR #3), two-tier review + plan-loop improvements (PR #4), observability + self-improvement layer (PR #5). The plan was for PR #6 to be the **real-project trial on `~/Desktop/Code/Boxette/call-details/`**. Pre-trial inspection of the target surfaced a blocking conflict: the target uses **uv** (Astral's Rust-rewrite of pip+venv), but the skill's Python templates assume `python3.12 -m venv venv && pip install`. Running the trial as-is would create a parallel `venv/` alongside the target's existing `.venv/` — two Python environments side by side, both real, mutually confusing.

We could have done the trial anyway and let "uv conflict" be its central finding. We already know that's the finding. Running the trial with no uv support would produce a report that just confirms what we know, and the report would be the only deliverable — no skill improvements would land. **Sequencing**: add uv support first (this PR #6), then trial second (PR #7).

Why uv-as-default for greenfield Python in 2026:

1. **Speed difference is felt most by non-developers.** Pip's slowness is invisible to seasoned developers (they've built tolerance). For a non-developer running `pip install` for the first time and waiting 30–60s for an innocuous command, it feels broken. uv finishes in 1–3s.
2. **uv hides the venv-activate dance.** Non-developers don't have to learn "activate", "deactivate", `./venv/bin/python`. `uv run pytest` just works.
3. **`uv python install 3.12`** removes the single most fragile step in any 2026 Python workflow for non-developers (macOS's system `python3` is 3.9.x; users get blocked here).
4. **Lockfile-by-default.** `uv.lock` is generated automatically — same "works on my machine" protection that `package-lock.json` provides in npm-land.
5. **Astral is already in the stack.** The skill ships `ruff` (Astral). Adding uv keeps the toolchain coherent.
6. **Industry direction**: by mid-2025, uv was the de-facto default for new Python project templates. By 2026 (now), telling a non-developer "use pip+venv" feels like teaching Subversion in 2015.

Why we still support pip (not uv-only):

- **Adoption-into-existing**: many existing projects use pip. The skill must respect the existing convention rather than force migration.
- **Explicit opt-out**: corporate/exotic environments may require pip. `--package-manager=pip` is the escape hatch.

User-decided scope constraints (pre-loop decisions, before iter-1):

- **Default for greenfield is uv** (not "stay backwards-compatible with pip default"). Non-developers benefit most from the modern path; existing pip projects are protected via auto-detect.
- **Auto-detection during `--apply` on an existing target**: heuristic based on file presence (`uv.lock`, `[tool.uv]` / `uv_build` markers in `pyproject.toml`, presence of `requirements*.txt`). When ambiguous, default to uv with an advisory print; never silently pick pip without a positive marker.
- **No `--python-version` flag** — `python_version` stays hardcoded to "3.12" in `_build_context` for now. uv mode's `.python-version` file uses the same value. Future PR can add a flag.
- **uv pin policy** (two distinct pins; both deliberate): (a) **Action ref is pinned** to `astral-sh/setup-uv@v8.1.0` exact tag (closes Codex iter-1 #5 + iter-3 #1 — `@v3` was years stale; bare `@v8` is an unpublished ref because setup-uv v8 doesn't publish floating major tags, only patch tags `v8.0.0` / `v8.1.0`; verified via `gh api repos/astral-sh/setup-uv/tags`). (b) **uv binary version is NOT pinned** — the action's default (latest stable uv) is what gets installed. Pre-loop user decision preserved. The `uv.lock` file is what guarantees per-project reproducibility — not the uv binary version. (Mirrors how pip-mode currently doesn't pin pip itself.) CI adds a `uv --version` diagnostic step so debug output captures the floated version. Action-ref bumps (`@v8.1.0` → `@v8.2.0` when v8.2 lands) are a manual periodic edit, same cadence as PR #3's gofumpt / golangci-lint pins.
- **Existing project's `pyproject.toml` is the source of truth for deps in adoption mode.** Greenfield uv mode writes a new minimal pyproject.toml with `[dependency-groups] dev` populated. **Adoption mode collision behaviour is the existing PR #1 contract** (closes Codex iter-1 #2 — earlier wording wrongly claimed a "skip-existing / write `.new`" path that doesn't exist in the codebase): `--apply` aborts on ANY pre-existing collision (`cli.py:257` — `collision detected — re-run with `--overwrite-existing` to consent`); user must pre-resolve via `--overwrite-existing` (overwrites everything) or by pre-deleting/renaming the colliding files. Adoption-mode UX redesign — the **analyze-then-decide-with-owner** contract (NOT a fixed per-file policy table; per user 2026-05-19) — ships in **PR #7 (hybrid: trial + adoption mode)**, NOT in PR #6. The trial against live `call-details/` provides the empirical data that informs the recommendation heuristics. See BACKLOG entry (c) for the design framing.
- **requirements-dev.txt is NOT emitted in uv mode** — uv reads `pyproject.toml`'s `[dependency-groups]` directly. Generating both creates a drift risk.
- **`.pre-commit-config.yaml` IS emitted in uv mode** (closes Codex iter-1 #3 — earlier draft contradicted itself by listing both "skip in uv mode" in Scope #4 AND "keep framework in uv mode" in Scope #9). The pre-commit framework is the hook engine in both modes; only the pytest entry's `entry:` line differs (`uv run python -m pytest` vs `./venv/bin/python -m pytest`).
- **Greenfield uv mode is "non-package" mode** (closes Codex iter-1 #1 — earlier draft wrongly specified `[build-system] = uv_build` while the scaffold only ships `src/main.py` as a loose module, not `src/<package>/__init__.py`). Per uv docs, `uv_build` (and most PEP 517 backends) expect a real package layout. The scaffold is a smoke project / starter — an application, not a library — so uv's "non-package" mode is the correct shape: `[project]` table present but no `[build-system]` table → uv doesn't try to build, only manages deps + the venv. Detection still treats `[build-system] build-backend = "uv_build"` as a positive uv marker for adoption (existing projects that DO use it as a build backend; PEP 517 kebab-case key per Codex Tier-2 #3).

### Bucket B — Python template uv-mode branches (in-place Jinja edits)

**Template-level safety convention** (Codex iter-5 #1): All Python-language and shared templates that branch on `package_manager` MUST use `{% if (package_manager | default("pip")) == 'uv' %}` (and similarly `{% if (package_manager | default("pip")) == 'pip' %}` for the explicit pip-branch form). Default to `"pip"` to preserve pre-PR-#6 rendering for non-aware callers.

## Architecture decisions specific to uv

- **Package manager default**: `uv` for greenfield Python; **auto-detect** for adoption (file presence in `--out` dir); explicit flag overrides everything.
- **Detection priority**: positive uv marker (`uv.lock`, `[tool.uv]`, `uv_build` backend) > positive pip marker (`requirements*.txt`) > ambiguous (pyproject present, no markers — manager=None, CLI defaults to uv) > malformed/greenfield (manager=None, CLI defaults to uv). Closes Claude iter-2 #1: rule 6 returns `(None, "ambiguous: ...")` not `("uv", "ambiguous: ...")` — the CLI applies the uv default; this keeps the "positive signal vs no positive signal" mental model clean and unblocks the ambiguous-specific override-hint advisory.
- **Advisory printing**: when `--package-manager` is explicit, no advisory. When detection returns a positive manager (rules 2-5), print succinct `"info: detected package_manager='<pm>' (<reason>)"`. When detection returns `(None, "ambiguous: ...")` and CLI defaults to uv, print explicit `"info: existing pyproject.toml has no uv/pip markers; defaulting package_manager='uv' (pass --package-manager=pip to override)"`. When detection returns `(None, "greenfield: ...")` or `(None, "malformed: ...")`, print nothing (greenfield default is unsurprising; malformed pyproject is the user's problem, not ours to advise on).
- **Detection runs in `main()`, not `_build_context`** (closes Claude iter-2 #6): `_build_context` stays a pure dict-construction function. The detection side-effect (filesystem stats, file reads, `tomllib.loads`) happens upstream in the apply runner; the resolved `package_manager` value flows into `_build_context` as a kwarg. Keeps existing tests that call `_build_context` with synthetic args from breaking.
- **Hook framework**: stays **`pre-commit`** (the framework, not the git event) in both modes. uv mode invokes the framework via `uv run pre-commit` (so the framework's own deps live in `.venv/`). pip mode unchanged. `.pre-commit-config.yaml` is **always rendered** (closes Codex iter-1 #3 — earlier draft had a contradiction). Rejected alternative: switching uv mode to native-git-hooks (PR #3 pattern for Go) — would diverge from PR #1's Python pattern more than necessary; the pre-commit framework works fine via `uv run`.
- **`.venv/` vs `venv/`**: uv writes to `.venv/` by default (its convention). pip mode writes to `venv/`. Generated `.gitignore` already ignores `venv/` in PR #1's template; uv-mode templates verify `.venv/` is also gitignored (small template diff if not — falls under Bucket B if needed).
- **Greenfield uv mode is "non-package" mode** (closes Codex iter-1 #1): greenfield uv-mode `pyproject.toml` has `[project]` table + `[dependency-groups]` but **no `[build-system]` table**. uv treats this as a "non-package" project — manages the venv + deps via `uv sync`, but never tries to build/install the project as a wheel. Correct for the smoke-project scaffold (an application starter, not a library). Rejected alternative: ship `uv_build` + restructure the scaffold to `src/<project_import_name>/__init__.py` (a real package) — adds a layout-restructure to the PR for a smoke-project that doesn't need to be importable. If a user later wants a library, they add `[build-system]` themselves (or a future BACKLOG entry adds a `--library` flag with the package-layout scaffold). For adoption mode, detection still treats `uv_build` backend as a positive uv marker (existing projects that DO use it).
- **No uv version pin in CI**: `astral-sh/setup-uv@v8.1.0` defaults to latest stable uv within the v8 major (closes Codex iter-1 #5 — v3 was years stale). `uv.lock` is what provides per-project reproducibility — not the uv binary version. (Mirrors how pip mode doesn't pin pip itself.) CI adds a `uv --version` diagnostic step for debug visibility. If floating-latest ever causes a flake, the BACKLOG entry "uv pin policy" covers pinning a specific version.
- **`.python-version` file**: written in uv mode only. Used by `uv python install` (and by pyenv/conda — broad compatibility). Single line: `3.12`. Pin tied to `python_version` context var.
- **Adoption-mode collision behaviour**: existing PR #1 safety contract is unchanged (closes Codex iter-1 #2 — earlier draft falsely claimed a skip-or-`.new` adoption mode that does not exist in `cli.py`). When `--apply` is run against an existing target with any pre-existing file collisions, the CLI aborts with `"collision detected — re-run with --overwrite-existing to consent, or use --diff first to see what would change"` (cli.py:257). User must (a) pass `--overwrite-existing` (overwrites every colliding file with the new template), or (b) pre-delete/rename the colliding files. **Adoption-mode UX redesign** — the analyze-then-decide-with-owner contract (per user 2026-05-19; see BACKLOG c for the 4-phase shape) — ships in **PR #7 (hybrid: trial + adoption mode)**. PR #6 does NOT attempt to design adoption-mode safety; it only adds uv support within the current PR #1 collision-abort contract.

## Lessons surfaced

Reviewer-proposed lessons (driver triages later — appends real ones to `LESSONS.md` in the writable impl session; rejects duplicates or project-local noise per the read-only / writable split rule).

1. **From iter-1.5 (driver, during manual consistency self-check)**: *"Plan-mode subagent runs via `make review-plan-consistency-by-claude` (AND `make review-plan-by-claude`) can return useless `'user declined the exit'` output when `--permission-mode plan` kicks in — the subagent generates findings, then politely declines ExitPlanMode (research task, not implementation), and the harness writes the decline line to the output file instead of the actual findings. Fall back to manual grep + side-by-side section read; the consistency-check discipline still applies. Fix scope is a Makefile target change (drop `--permission-mode plan` OR add explicit `do NOT call ExitPlanMode` instruction to the prompt) — captured as BACKLOG (f) for impl in PR #6."*

2. **From iter-2 (Claude reviewer, finding #1)**: *"After a fold, re-check that conjunctions across N branches don't include a guarantee-false combination. The 'manager is None AND reason starts with X' guard in the CLI advisory was logically dead because the detect.py rule that produces 'reason starts with X' also produces a non-None manager. Same shape: a fold's two parts can independently look correct yet jointly leave dead code. Mitigation: when folding a finding touches multiple methods/sections, write out the truth table of branch conditions before saving — easier to spot 'this branch can never fire' on paper than in code."* (Trigger: PR #6 iter-2 review of the iter-1 fold.)

3. **From iter-3 (driver, after user push-back at human-approval gate)**: *"After folding a reviewer's findings, ALWAYS re-run the SAME reviewer to confirm 0 imp-3 before declaring convergence. A different reviewer's 0-imp-3 verdict (e.g. Claude after Codex flagged 3 imp-3) is independent evidence of plan quality, but it is NOT proof that the original reviewer's specific concerns are resolved — different reviewers find different things. The convergence test is 'the reviewer that flagged imp-3 now sees 0 imp-3', not 'some reviewer sees 0 imp-3'. PR #5's precedent: 6 Codex iterations until Codex itself returned 0 imp-3 plateau. The user's push-back at PR #6's human-approval gate ('have we finished our codex + self review loop? 0 imp-3 by codex?') saved the loop from declaring premature convergence; the re-run surfaced a real CI blocker (`@v8` unpublished ref) that would have failed PR #6's impl PR."* (Trigger: PR #6 iter-3.)

4. **From iter-5 (Codex reviewer, finding #1)**: *"When adding any new Jinja conditional (`{% if X == 'foo' %}`) to a shared template, audit EVERY render context across the codebase (production code paths + tests + any handwritten context dicts) to ensure the new key X is present — or alternatively use the `\|default("safe-fallback")` filter as a template-side safety net. The project's `jinja2.Environment(undefined=jinja2.StrictUndefined)` config means a missing key crashes the render, not a silent fallback. PR #6's iter-5 caught a real impl-PR-`make check`-killer: adding `{% if package_manager == 'uv' %}` to `shared/CLAUDE.md.tmpl` would have crashed `tests/test_triage_byte_identity.py:39`'s `SKILL_REPO_CONTEXT` render. The `\|default("pip")` filter is the cheap defensive choice — preserves pre-existing rendering for non-aware callers."* (Trigger: PR #6 iter-5.)
