# Skill PR #6 — uv support for Python

> Adds `--package-manager={uv,pip}` to the `dev-project-setup` skill's Python language. **uv is the new default for greenfield Python projects**; pip-venv stays supported for adoption-into-existing-projects + explicit opt-out. Auto-detection picks the right mode when applying onto an existing project. Mirrors PR #3's structural pattern (additive variant within an existing language, not a new language).

## Context

PR #1–#5 shipped: Python (PR #1), Node-TS (PR #2), Go (PR #3), two-tier review + plan-loop improvements (PR #4), observability + self-improvement layer (PR #5). The plan was for PR #6 to be the **real-project trial on `~/Desktop/Code/Boxette/call-details/`**. Pre-trial inspection of the target surfaced a blocking conflict: the target uses **uv** (Astral's Rust-rewrite of pip+venv), but the skill's Python templates assume `python3.12 -m venv venv && pip install`. Running the trial as-is would create a parallel `venv/` alongside the target's existing `.venv/` — two Python environments side by side, both real, mutually confusing.

We could have done the trial anyway and let "uv conflict" be its central finding. We already know that's the finding. Running the trial with no uv support would produce a report that just confirms what we know, and the report would be the only deliverable — no skill improvements would land. **Sequencing**: add uv support first (this PR #6), then trial second (PR #7).

Why uv-as-default for greenfield Python in 2026:

1. **Speed difference is felt most by non-developers.** Pip's slowness is invisible to seasoned developers (they've built tolerance). For a non-developer running `pip install` for the first time and waiting 30–60s for an innocuous command, it feels broken. uv finishes in 1–3s.
2. **uv hides the venv-activate dance.** Non-developers don't have to learn "activate", "deactivate", `./venv/bin/python`. `uv run pytest` just works.
3. **`uv python install 3.12`** removes the single most fragile step in any 2026 Python workflow for non-developers (macOS's system `python3` is 3.9.x; users get blocked here).
4. **Lockfile-by-default.** `uv.lock` is generated automatically — same "works on my machine" protection that `package-lock.json` provides in npm-land.
5. **Astral is already in the stack.** The skill ships `ruff` (Astral). Adding uv keeps the toolchain coherent.
6. **Industry direction**: by mid-2025, uv was the de-facto default for new Python project templates. By 2026 (now), telling a non-developer "use pip+venv" feels like teaching Subversion in 2015.

Why we still support pip (not uv-only):

- **Adoption-into-existing**: many existing projects use pip. The skill must respect the existing convention rather than force migration.
- **Explicit opt-out**: corporate/exotic environments may require pip. `--package-manager=pip` is the escape hatch.

User-decided scope constraints (pre-loop decisions, before iter-1):

- **Default for greenfield is uv** (not "stay backwards-compatible with pip default"). Non-developers benefit most from the modern path; existing pip projects are protected via auto-detect.
- **Auto-detection during `--apply` on an existing target**: heuristic based on file presence (`uv.lock`, `[tool.uv]` / `uv_build` markers in `pyproject.toml`, presence of `requirements*.txt`). When ambiguous, default to uv with an advisory print; never silently pick pip without a positive marker.
- **No `--python-version` flag** — `python_version` stays hardcoded to "3.12" in `_build_context` for now. uv mode's `.python-version` file uses the same value. Future PR can add a flag.
- **uv pin policy**: uv itself moves fast (~weekly releases). We do NOT pin a specific uv version in CI; we use `astral-sh/setup-uv@v8` (closes Codex iter-1 #5 — v3 was years stale; v8 is current major per `gh api astral-sh/setup-uv/releases/latest`, v8.1.0 published 2026-04-16) with the action's default (latest stable uv within the v8 major). Generated projects use whatever uv the user has installed. The `uv.lock` file is what guarantees reproducibility — not the uv binary version. (Mirrors how pip-mode currently doesn't pin pip itself.) CI adds a `uv --version` diagnostic step so debug output captures the floated version.
- **Existing project's `pyproject.toml` is the source of truth for deps in adoption mode.** Greenfield uv mode writes a new minimal pyproject.toml with `[dependency-groups] dev` populated. **Adoption mode collision behaviour is the existing PR #1 contract** (closes Codex iter-1 #2 — earlier wording wrongly claimed a "skip-existing / write `.new`" path that doesn't exist in the codebase): `--apply` aborts on ANY pre-existing collision (`cli.py:257` — `collision detected — re-run with `--overwrite-existing` to consent`); user must pre-resolve via `--overwrite-existing` (overwrites everything) or by pre-deleting/renaming the colliding files. Adoption-mode UX redesign (a real skip-or-merge contract) is parked — the PR #7 real-project trial on `call-details/` is the UX-discovery vehicle for that design.
- **requirements-dev.txt is NOT emitted in uv mode** — uv reads `pyproject.toml`'s `[dependency-groups]` directly. Generating both creates a drift risk.
- **`.pre-commit-config.yaml` IS emitted in uv mode** (closes Codex iter-1 #3 — earlier draft contradicted itself by listing both "skip in uv mode" in Scope #4 AND "keep framework in uv mode" in Scope #9). The pre-commit framework is the hook engine in both modes; only the pytest entry's `entry:` line differs (`uv run python -m pytest` vs `./venv/bin/python -m pytest`).
- **Greenfield uv mode is "non-package" mode** (closes Codex iter-1 #1 — earlier draft wrongly specified `[build-system] = uv_build` while the scaffold only ships `src/main.py` as a loose module, not `src/<package>/__init__.py`). Per uv docs, `uv_build` (and most PEP 517 backends) expect a real package layout. The scaffold is a smoke project / starter — an application, not a library — so uv's "non-package" mode is the correct shape: `[project]` table present but no `[build-system]` table → uv doesn't try to build, only manages deps + the venv. Detection still treats `[build-system] backend = "uv_build"` as a positive uv marker for adoption (existing projects that DO use it as a build backend).

- **No migration tool** (e.g. "convert this pip project to uv"). Adoption mode respects what the user has. Future PR.
- **No deprecation of pip mode.** Both modes are first-class for the foreseeable future.
- **No nodejs/go test parametrisation changes.** They remain single-toolchain.
- **No changes to PR #5's `make status` target.** Status output is package-manager-agnostic.
- **No real-project trial in this PR.** That's PR #7.

## Architecture decisions specific to uv

- **Package manager default**: `uv` for greenfield Python; **auto-detect** for adoption (file presence in `--out` dir); explicit flag overrides everything.
- **Detection priority**: positive uv marker (`uv.lock`, `[tool.uv]`, `uv_build` backend) > positive pip marker (`requirements*.txt`) > ambiguous (pyproject present, no markers — manager=None, CLI defaults to uv) > malformed/greenfield (manager=None, CLI defaults to uv). Closes Claude iter-2 #1: rule 6 returns `(None, "ambiguous: ...")` not `("uv", "ambiguous: ...")` — the CLI applies the uv default; this keeps the "positive signal vs no positive signal" mental model clean and unblocks the ambiguous-specific override-hint advisory.
- **Advisory printing**: when `--package-manager` is explicit, no advisory. When detection returns a positive manager (rules 2-5), print succinct `"info: detected package_manager='<pm>' (<reason>)"`. When detection returns `(None, "ambiguous: ...")` and CLI defaults to uv, print explicit `"info: existing pyproject.toml has no uv/pip markers; defaulting package_manager='uv' (pass --package-manager=pip to override)"`. When detection returns `(None, "greenfield: ...")` or `(None, "malformed: ...")`, print nothing (greenfield default is unsurprising; malformed pyproject is the user's problem, not ours to advise on).
- **Detection runs in `main()`, not `_build_context`** (closes Claude iter-2 #6): `_build_context` stays a pure dict-construction function. The detection side-effect (filesystem stats, file reads, `tomllib.loads`) happens upstream in the apply runner; the resolved `package_manager` value flows into `_build_context` as a kwarg. Keeps existing tests that call `_build_context` with synthetic args from breaking.
- **Hook framework**: stays **`pre-commit`** (the framework, not the git event) in both modes. uv mode invokes the framework via `uv run pre-commit` (so the framework's own deps live in `.venv/`). pip mode unchanged. `.pre-commit-config.yaml` is **always rendered** (closes Codex iter-1 #3 — earlier draft had a contradiction). Rejected alternative: switching uv mode to native-git-hooks (PR #3 pattern for Go) — would diverge from PR #1's Python pattern more than necessary; the pre-commit framework works fine via `uv run`.
- **`.venv/` vs `venv/`**: uv writes to `.venv/` by default (its convention). pip mode writes to `venv/`. Generated `.gitignore` already ignores `venv/` in PR #1's template; uv-mode templates verify `.venv/` is also gitignored (small template diff if not — falls under Bucket B if needed).
- **Greenfield uv mode is "non-package" mode** (closes Codex iter-1 #1): greenfield uv-mode `pyproject.toml` has `[project]` table + `[dependency-groups]` but **no `[build-system]` table**. uv treats this as a "non-package" project — manages the venv + deps via `uv sync`, but never tries to build/install the project as a wheel. Correct for the smoke-project scaffold (an application starter, not a library). Rejected alternative: ship `uv_build` + restructure the scaffold to `src/<project_import_name>/__init__.py` (a real package) — adds a layout-restructure to the PR for a smoke-project that doesn't need to be importable. If a user later wants a library, they add `[build-system]` themselves (or a future BACKLOG entry adds a `--library` flag with the package-layout scaffold). For adoption mode, detection still treats `uv_build` backend as a positive uv marker (existing projects that DO use it).
- **No uv version pin in CI**: `astral-sh/setup-uv@v8` defaults to latest stable uv within the v8 major (closes Codex iter-1 #5 — v3 was years stale). `uv.lock` is what provides per-project reproducibility — not the uv binary version. (Mirrors how pip mode doesn't pin pip itself.) CI adds a `uv --version` diagnostic step for debug visibility. If floating-latest ever causes a flake, the BACKLOG entry "uv pin policy" covers pinning a specific version.
- **`.python-version` file**: written in uv mode only. Used by `uv python install` (and by pyenv/conda — broad compatibility). Single line: `3.12`. Pin tied to `python_version` context var.
- **Adoption-mode collision behaviour**: existing PR #1 safety contract is unchanged (closes Codex iter-1 #2 — earlier draft falsely claimed a skip-or-`.new` adoption mode that does not exist in `cli.py`). When `--apply` is run against an existing target with any pre-existing file collisions, the CLI aborts with `"collision detected — re-run with --overwrite-existing to consent, or use --diff first to see what would change"` (cli.py:257). User must (a) pass `--overwrite-existing` (overwrites every colliding file with the new template), or (b) pre-delete/rename the colliding files. **Adoption-mode UX redesign** — a real skip-or-merge contract with per-file decisions — is parked in BACKLOG; the PR #7 real-project trial on `call-details/` is the UX-discovery vehicle. PR #6 does NOT attempt to design adoption-mode safety; it only adds uv support within the current contract.

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| uv detection misfires on edge cases (e.g. project has both `uv.lock` and `requirements.txt` during a migration) | Detection prioritizes positive uv markers (covers migration "starting to use uv" direction). Tests (j) + (k) exercise both-markers cases explicitly. Advisory printing (with the detection `reason`) surfaces the choice so user can override via `--package-manager=pip`. |
| `astral-sh/setup-uv@v8` action default-latest could break CI without a repo diff | Accepted trade-off per PR #3's gofumpt pin precedent + the pre-loop user decision to not pin uv: pinning churn vs floating-latest. CI's `uv --version` diagnostic step captures the version that ran so a flake can be diagnosed. BACKLOG entry tracks pinning the action's `version:` input if floating-latest ever bites. Tests use `shutil.which("uv")` so local smoke still works without the action. |
| Existing pyproject.toml when running `--apply` adoption | PR #1's safety contract fires: `--apply` aborts with "collision detected" message + lists colliding files; exit 2. User passes `--overwrite-existing` to consent (overwrites everything) or pre-deletes/renames the colliding files. PR #6 does not change this; adoption-mode UX redesign is parked. Detection unit tests cover the detection signal; the trial in PR #7 will surface the user-facing UX gap. |
| User installs the skill but doesn't have uv on PATH | (a) Skill-repo's `make doctor` includes uv advisory check (PR #6 Bucket E). (b) Generated `make install` in uv mode fails with a uv-specific error message (escape hatch: re-run with `--package-manager=pip`). (c) `docs/usage.md` mentions the install one-liner for uv (`brew install uv` / `curl ... \| sh` / `pipx install uv`). |
| Tests pass locally but the uv smoke walk silently skips in CI when `uv` isn't on PATH | Mirror PR #3's `CI=true` pattern — `test_smoke_python_uv_generated.py` uses `pytest.skip(...)` locally but `pytest.fail(...)` when `CI=true`. Skill-repo CI explicitly installs `astral-sh/setup-uv@v8` so the fail-hard path never fires there. |
| Drift between uv-mode pin list and pip-mode pin list (ruff/pytest/pre-commit versions) | Template tests use a single canonical pin list (Python module-level constant or pytest fixture); both modes' tests assert against it. Drift fails the test. |
| Greenfield uv mode "non-package" decision becomes wrong when user wants to build a library | Documented in Architecture decisions: user adds `[build-system]` themselves when they need it. Future BACKLOG entry: `--library` flag with package-layout scaffold. Acceptable now — the skill's audience is non-developer / app-style projects, not library publishing. |
| Existing CLAUDE.md is a common adoption case (per call-details inspection) | Standard PR #1 collision-abort fires for CLAUDE.md too. User must consent via `--overwrite-existing` (loses target's CLAUDE.md content) or pre-rename target's CLAUDE.md before `--apply`. PR #7 real-project trial will surface UX gaps in the merge experience and feed a future BACKLOG entry for "CLAUDE.md merge" / "adoption-mode skip-or-merge". NOT in scope for PR #6. |
| `uv` not on PATH at `git push` time (uv mode only) (closes Claude iter-2 #9) | Generated uv-mode `.pre-commit-config.yaml`'s pre-push hook runs `entry: uv run python -m pytest`. If `uv` isn't on the shell PATH at `git push` time (e.g. push via an IDE shell that doesn't load the user's PATH; pushes from CI runners that don't have uv installed), the pre-push hook silently fails. Pip mode's `entry: ./venv/bin/python -m pytest` is an absolute path, immune to this. Mitigation: `docs/usage.md`'s new "Python: uv vs pip" section documents the constraint + recommends adding uv install to the user's `~/.zshrc` / `~/.bashrc`. Escape hatch: `git push --no-verify`. Future BACKLOG entry: extend `make install-hooks` to verify `uv` is reachable from a login shell before installing the hook. |

## What we are NOT doing in this PR

- **No `--python-version` CLI flag.** Hardcoded "3.12" stays.
- **No migration tool (pip → uv conversion).** Adoption respects existing tooling.
- **No deprecation of pip mode.** Both modes are first-class.
- **No real-project trial.** That's PR #7. (Closes Claude iter-2 #10) — **scope constraint for PR #7 trial design**: `call-details/` already has every file the skill writes (CLAUDE.md, pyproject.toml, README.md, tests/, src/, uv.lock). With PR #6's current adoption contract (collision-abort unless `--overwrite-existing`), PR #7's trial against the live `call-details/` is `--dry-run` / `--diff` only. `--apply` would either (a) abort cleanly (status quo) or (b) destroy the user's real work (`--overwrite-existing`). To exercise the full `--apply` flow during PR #7, the trial needs either (i) a fixture copy of call-details (call-details-trial-fixture/), or (ii) the adoption-mode UX redesign that's parked in BACKLOG (c). PR #7's plan-loop should pick one explicitly.
- **No uv equivalent for Node-TS or Go.** Their native managers (npm, go mod) are already optimal.
- **No uv pin in CI.** Floating `astral-sh/setup-uv@v8` default-latest. Trade-off documented; `uv --version` diagnostic step added.
- **No adoption-mode UX redesign.** Current PR #1 contract — collision-abort unless `--overwrite-existing` — stays unchanged in PR #6. PR #7 trial is the UX-discovery vehicle for a future skip-or-merge contract. CLAUDE.md merge is part of this same parked-design.
- **No `pre-commit` framework removal in uv mode.** Stays. Just invocation changes.
- **No library-style package scaffold.** Greenfield uv mode is "non-package" (`[project]` without `[build-system]`). A `--library` flag with `src/<package>/__init__.py` layout is parked.
