## Architecture decisions specific to Node-TS

- **Node version**: hardcoded `node_version = "24"` (Active LTS as of 2026-05-15) in `_build_context` for PR #2, parallel to PR #1's `python_version = "3.12"` hardcoding. Node 20 EOL'd 2026-04-30 (closes Codex iter-1 #3 — original draft pinned 20 which is now unsupported). Node 22 is Maintenance LTS; Node 24 is Active LTS, so 24 is the right pin for new projects shipping in 2026. Variable still flows through context so a future PR (or `--node-version` flag) can override.
- **Package manager**: `npm` only. No yarn / pnpm / bun support in PR #2 (parked).
- **Linter + formatter**: Biome (single binary, no eslint + prettier coordination drift). The master plan in Boxette commits to this choice.
- **Test runner**: vitest (master plan choice).
- **Type-check command**: `tsc --noEmit` — runs as part of `make check` after lint and test.
- **TypeScript ESM**: `package.json` has `"type": "module"`; tsconfig uses `module: "NodeNext"`. Pure-ESM is the modern Node-TS path; matches the framework-agnostic generic-Node positioning.
- **Hook framework**: **Husky + lint-staged** (closes Codex iter-1 #2). Decided over the `pre-commit` framework that PR #1 uses for Python. Rationale: (a) Husky is Node-native (no Python dependency for Node-only projects); (b) the user-facing Makefile surface stays identical across languages — `make install-hooks` is the developer's interface, the underlying tool is hidden; (c) `package.json` `"prepare"` script auto-arms hooks on `npm install`, no manual step needed after first clone. The trade-off documented: cross-language consistency lives at the *Makefile target* level, not at the *underlying-tool* level. This is an autonomous decision in iter-2 of this plan; surfaced for user sign-off at the mandatory-approval gate.
- **First-install path**: `make install` runs `npm install` (NOT `npm ci`) — closes Codex iter-1 #1. The first `npm install` generates `package-lock.json` which the user commits; subsequent CI runs use `npm ci` from that committed lockfile. The skill itself doesn't ship a `package-lock.json.tmpl` (lockfiles for unpublished projects shouldn't be pre-generated by an external skill — the user's first `npm install` resolves whatever majors are pinned in `package.json.tmpl`). Documented in `docs/usage.md`'s post-bootstrap section: "first step after `make install`: `git add package-lock.json && git commit -m 'Pin Node deps'`".

## Risks + mitigations (PR-#2-specific)

| Risk | Mitigation |
|---|---|
| Node ecosystem version churn (Biome, vitest, TypeScript, Husky) | Caret-pin majors in `package.json.tmpl`; user commits `package-lock.json` after first `npm install` for actual version pinning (closes Codex iter-3 #3 — terminology corrected: caret ranges aren't "concrete pins", lockfile is). Document the bump flow in `shared/CONTRIBUTING.md.tmpl` (language-conditional section: `npm outdated` + `npm install <pkg>@latest` for Node). Reasonable cadence: review pins every ~6 months |
| `npm install` slow on smoke walk (~60-120s cold) | Smoke test gets 180s timeout; node-not-on-PATH path uses `pytest.skip`. Local devs running `make check` repeatedly aren't impacted (pytest-cache + the fact that the smoke test creates a per-test tempdir and only `npm install`s once per run) |
| `tsconfig.json` is JSON-with-comments (technically JSONC) — Python's `json.loads` would choke | PR #2's shipped `tsconfig.json.tmpl` is strict JSON (no comments, no trailing commas). Documented in Bucket B. `tests/test_nodejs_templates.py` uses `json.loads` directly |
| `biome.json` strict-JSON discipline same as tsconfig | Same approach: strict JSON in the shipped template, `json.loads` in the test |
| `node` not on PATH on developer's machine → smoke test fails | `test_smoke_nodejs_generated.py` uses `shutil.which("node")` to check up front; skips with `pytest.skip("node not on PATH")` rather than fail. Parallel to how `test_canonical_check_order.py` handles missing pre-3.12 python |
| Husky `prepare` script fails silently in CI (CI may run `npm ci --ignore-scripts`) | The generated `make install-hooks` target is explicit + idempotent: `npx husky` (Husky v9 canonical setup; closes Codex iter-2 #2 + iter-5 P2). This invokes the same logic the `prepare` script does — creates `.husky/_/` shim layer, sets `core.hooksPath = .husky/_`, registers per-hook shims. The `.husky/pre-commit` + `.husky/pre-push` files are shipped by bootstrap as part of Bucket B, so they exist on disk regardless of whether the `prepare` script ran. CI doesn't need hooks (pre-commit/pre-push are local-only), so `--ignore-scripts` on CI is fine. Documented in CLAUDE.md.tmpl's nodejs branch |
| `.husky/pre-commit` + `.husky/pre-push` are manifest-tracked; `.husky/_/` is NOT (and shouldn't be — it's third-party runtime output) | (Closes Codex iter-3 #1 + Claude iter-4 #3.) Bucket B ships `.husky/pre-commit.tmpl` + `.husky/pre-push.tmpl` via `manifest.plan_entries()`. **However**, Husky v9's `prepare` script (`"husky"` in package.json) runs during `npm install` and creates `.husky/_/husky.sh` + other runtime support files. Those files exist AFTER `npm install`, NOT after bootstrap apply — they're outside the manifest by design (same regime as PR #1's `.git/hooks/` — bootstrap doesn't manage tool-created runtime files). **Restore semantics**: `--restore` cleanly removes `.husky/pre-commit` + `.husky/pre-push` BEFORE any `npm install` runs (greenfield rollback). If the user already ran `npm install` (so `.husky/_/` exists), `--restore` removes the manifest-tracked files but `.husky/_/` remains (parallel to PR #1's note that `.git/hooks/` survives `--restore`). Documented in the smoke walk's ordering (steps 1-3 happen BEFORE step 4 `make install`). New test in `tests/test_smoke_nodejs_generated.py` asserts `--restore` removes the manifest files; a separate test asserts `--restore` after `npm install` leaves `.husky/_/` but cleanly removes `.husky/pre-commit` + `.husky/pre-push` |
